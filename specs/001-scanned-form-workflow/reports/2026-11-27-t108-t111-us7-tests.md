## T108 — failed/interrupted export leaves no final artifact (FR-072; SC-010)

The test runs the production composition on the emulator and proves four
phases in one journey:

1. **Real IO failure.** The debug-only artifact-directory probe toggles the
   owner-write bit of `cacheDir/feldexa_exports`; the production
   `ExportController` then calls the native applier, which cannot create its
   temporary file and reports `EXP-002`. The probe shows `pdfCount=0`,
   `tmpCount=0` after the failure.
2. **Preflight failure.** An overflowing value (the production `setFieldValue`
   command with a value far longer than the recognised 300 × 18 pt field; the
   edit command itself refuses an out-of-page rect) makes
   `ExportController.prepare` return `ExportPreparationBlocked` with `EXP-001`;
   no port is called and the artifact directory stays empty.
3. **Success control.** A valid snapshot still exports and publishes exactly
   one artifact, so the empty directories above are not a probe artifact.
4. **Interrupted save.** The preview's „Speichern“ opens the SAF picker; the
   host driver cancels it with BACK. The preview reports no failure and no
   success, the artifact stays readable, and closing the preview deletes it
   (`EXP-002` reads afterwards), leaving the artifact directory empty.

Evidence directory: `artifacts/2026-11-27-t108-export-failure/`.

## T109 — two-page export and artifact verification (FR-069/FR-073; SC-005/SC-006)

The fourth leg of the existing production export journey imports `sf-001.pdf`,
confirms the fixture-declared „Familienname“ text field, and adds, through the
production edit commands, one checked and one unchecked checkbox and two
signatures (one per page). It asserts after save and reopen that

- the text field keeps `Provenance.machine` and its source suggestion id,
- the four seeded fields keep `Provenance.user`,
- the checked/unchecked checkbox values and both `SignatureValue`/`SignatureMark`
  pairs survive,
- the suggestion list survives save and reopen.

The artifact is picked up by the host driver and verified with the T105 harness
(`tools/pdf_verify/verify_artifact.py`, qpdf 12.4.2 + MuPDF 1.28.5 + Poppler)
using expectations derived from the test's own field rects:

```json
{"fields": [{"page": 1, "rect": [190.0, 148.0, 300.0, 18.0], "type": "text", "value": "Müller"}],
 "marks": [{"page": 1, "rect": [190.0, 502.0, 10.0, 10.0], "type": "checkbox", "expected": "marked"}, …],
 "masks": [ … the same five rects … ]}
```

Rows exercised on artifact 4: structural validity, page count/order, geometry,
masked appearance diff outside the rects, value placement, text content, no
clipping, checkbox states (marked + empty), signatures, no interactive controls,
printability (two engines), source integrity. Artifact isolation remains the
driver's own probe.

Measured result on the picked-up artifact (HEAD `20d24c`, marker-derived
expectations): **artifact 4 = 12 PASS, 0 FAIL, 0 PARTIAL, 1 NOT_RUN** (artifact
isolation, covered by T108). Artifacts 1 and 2: 10 PASS/0 FAIL/3 NOT_RUN each;
artifact 3 (AcroForm source, no field expectations): 6 PASS/0 FAIL/1 PARTIAL/
6 NOT_RUN. The placement rows of artifacts 1 and 2 are `PROVEN` (origin metric,
≤ 2.835 pt). The picked-up PDFs were deleted after verification; their digests
are in `artifact-*-pickup.txt`.

Evidence directory: `artifacts/2026-11-27-t109-export-harness/`.

## T110 — Android print preview and two independent engines (SC-005; CHK019)

**Result: `BLOCKED` (environment), no PASS claimed.**

The test and driver are delivered (`integration_test/print_test.dart`,
`tools/android/t108_t110_drive.py print`): they export a filled two-page
artifact, open the production preview, tap „Drucken“, have the driver capture
the system print preview (activity + `dumpsys print` + screenshot), cancel it
with BACK, pick the artifact up with `run-as`, run the T105 harness, and
pixel-compare Poppler and MuPDF renderings per page.

The device run did not start: after the T109 runs the shared build permit was
held by another job and the driver remained queued past the run window, and the
preceding build had already shown the known environment stall (a 10-minute
Gradle task). No third device attempt was made, per the run-window rule. The
printability evidence that does exist is the T105 harness on the T109 artifact 4
(`artifacts/2026-11-27-t109-export-harness/harness-artifact-4.json`):

- `printability` **PASS** — Poppler and MuPDF rendered both pages at 300 dpi,
- `page count and order`, `page geometry`, `text content`,
  `no interactive controls`, `source integrity` **PASS**.

What is missing and must not be implied: the Android print preview was not
observed, and the Poppler-vs-MuPDF pixel comparison of this test did not run.
T110 therefore stays **BLOCKED** with no evidence directory of its own.

## T111 — SIMULATED watermark and non-production labelling (FR-087; §7)

The host entry test (`@TestOn('vm')`) drives the real `SimulatedPdfExportAdapter`
over the committed `sf-001.pdf` catalogue entry and asserts

- the adapter descriptor is simulated and claims neither PDFBox compatibility
  nor print fidelity,
- every preview page carries the visible `SIMULATED` watermark and the German
  `kein Produktions-PDF` footer,
- the plan and result carry `evidenceClass: simulated`,
- the preview bytes are deterministic across two exports.

The browser lane is `NOT_RUN`: the Flutter browser runner hangs on this host
(`run-tscn02hu/reports/findings/2026-11-27-flutter-browser-lane-hang.md`), so no
browser, `DEVICE`, or `EMULATOR` claim is made from this test.
