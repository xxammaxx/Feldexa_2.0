**Correction-1 — proven OCR quality defect and its fix (host-verified).**

*Root cause (label/type association).* `TypeInference` treated a printed label as
credible only inside a 24 pt Euclidean gap. The reference form, like an ordinary
authority form, prints each field label in a left column and the input region in
a second column, so the real label-to-field gap is 14–90 pt and grows with the
label's own length. On the reference variant that left 9 of 13 fields without
any label, gave the remaining ones the nearest heading or printed mask instead
of their label, and forced 12 of 13 suggestions to `multiline`; the pre-fix
reference measured label accuracy 0.00 % with 8 unresolved labels (post-fix:
76.92 %, 1 unresolved).

*Fix (production, minimal).* `packages/feldexa_recognition/lib/src/type_inference.dart`
now associates a label printed on the candidate's own row (overlapping vertical
spans, and not printed mostly inside the candidate region) and ranks a same-row
label above a nearer line above or below. This is the documented cue semantics of
`ocr_alignment_right`; the 24 pt radius still governs all off-row labels, so the
proximity contract for headings and neighbouring rows is unchanged. No threshold,
golden datum, ground truth, expected text, or threshold value was touched, and no
recognized character is substituted, normalized, or rewritten.

*RED/GREEN (check 12 → checks 6/13).* Three new tests in
`packages/feldexa_recognition/test/type_inference_test.dart` pin the defect and
fail at the pre-fix bytes of `type_inference.dart` (commit `40a4260`):

- `a left label on the same row is associated beyond 24 pt`
- `a same-row left label wins over a heading line above`
- `a printed mask inside the candidate is not the structural label`

RED: 55 passed, 3 failed (exit 1). GREEN after the fix: 58 passed, 0 failed
(exit 0). Three pre-existing T053 tests were updated because they pinned the old
fixed-radius outcome for same-row labels (the boundary and tie-break cases now use
off-row positions, where the 24 pt rule still applies); one guardrail test
(`a label two rows above is still not a same-row label`) passes before and after
and prevents over-acceptance. Post-fix file hashes: `type_inference.dart`
`a2757ea0f6f972425d631b95966ca555869ec403693bad57c098e8b82566e367`,
`type_inference_test.dart`
`2ef4975a8325cdb3c9246dee5e32cf319c2adee67946f010da0b0e7aa4f16e53`.

**Correction-2 — the 3° skew defect (verified, measured on device).**

*Root cause (pre-correction state).* The pipeline had no deskew stage: the
injected 3° raster reached the recognizer tilted, so lines merged or disappeared (30/51 associated) and the
returned boxes were too tall and too far from the annotated rows.

*Fix (production, minimal).* A new pure-math stage
`SkewCorrection.kt` estimates the dominant row skew with a projection-profile
search (±5°, 0.25° steps over ink-thresholded, subsampled luminance), rotates the
raster upright with bilinear sampling on a white background, and maps the
recognizer's rectangles back into the original raster frame;
`MlKitTextRecognizer.recognize` applies it before ML Kit. A raster whose estimate
is below 1.0° is passed through untouched, which is why every upright variant
keeps its exact pre-fix values. No recognized text is read, rewritten or
substituted.

*RED/GREEN (checks 14/15).* At the pre-fix baseline `correctionFor` returned no
correction and exactly the three deskew/symmetry tests failed (the three no-op
and identity tests passed): `./gradlew --no-daemon …` exit 1. After the fix the
same command over `SkewCorrectionTest` and `MlKitOcrServiceTest` is
`BUILD SUCCESSFUL` (exit 0). The Gradle daemon was stopped after the run.

*Measured effect (class-run report §5.8).* `scan-200dpi-skew-3deg` moves from CER
48.48 % / special recall 68.27 % / type accuracy 0.00 % (FAIL) to CER 15.42 % /
87.50 % / 100.00 % (PASS) with the pre-declared thresholds unchanged, and the six
other variants keep their exact pre-fix character metrics. The correction-1
label/type fix is now measured on device as well: label accuracy 0.00 % → 69.23 %
on the clean variants, 7.69 % → 84.62 % on the degraded ones, unresolved labels
8 → 1.

*Driver pull correction.* The correction-1 tar-based run-file pull produced a
non-tar stream (`exec-out` output was not a valid archive) and the first
correction-2 attempt lost its run files to the runner's uninstall. The driver now
pulls both files with `adb exec-out run-as cat`, verifies each as non-empty JSON
before scoring, and retries up to ten times; the successful attempt is recorded in
the class-run evidence.

**Correction-3 — review findings on the correction-2 candidate.**

Both independent reviews failed correction-2. Correction-3 closes the code
findings and one reporting defect, each with a RED/GREEN test:

- *A1 inverse rect mapping* (checks 16/17). `mapRectBack` applied the same
  rotation direction `rotate` already applies, so deskewed boxes were rotated
  twice. It now uses `R(+correction)`; a known-point round-trip test fails at the
  correction-2 bytes and passes after the fix.
- *A3 AABB clamp* (checks 16/17). Mapped boxes are clamped to the raster bounds;
  an edge-rectangle test fails before and passes after.
- *A2 label direction and overlap* (checks 18/19). `_sharesRow` accepted any
  label with any vertical overlap on any side; it now requires the label's right
  edge at or before the candidate's left edge (2 pt tolerance) and at least half
  of the shorter box overlapping. A right-side value line and a one-point top
  sliver are rejected; a tall multiline candidate still associates its left
  label. Dart RED 59 passed / 2 failed → GREEN 61/61.
- *B4 verbatim scope* (check 20). The scorer's "silent normalization" reason
  compared a suggestion label with the run record's OCR lines from the test's own
  capture-DPI recognition, while `AnalyzeDocument` recognises its own 200 DPI
  raster. The three differing labels in the 150/300 DPI variants
  (`Straße und Hausnummner`, `TT.MM.JJ`, `D Einverständnis erteilt`) are therefore
  **content differences from a second raster**, not whitespace and not a product
  normalization. The check now applies only to 200 DPI captures and classifies
  the rest as not comparable; a new Python regression test pins both cases. This
  is a correctness fix to a false FAIL reason, not a threshold change: the
  pre-declared CER and special-recall floors are untouched, and the two variants
  pass because they meet those floors.
- *B7 provenance* (this correction's process). The code and tests were committed
  first (`3102557`), the seven variants were then re-run at that committed HEAD,
  and the evidence is committed afterwards. The run-time tree was dirty only with
  the CRLF `gradlew.bat` and the driver's pull-poller fix (committed here); the
  run record's `git-identity.txt` and the report's §5.9 carry those hashes, and
  `fixture-sha256.txt` now labels the fixture hash `fixture_pdf_sha256`.

**Correction-4 — frame-correct skew measurement and test hygiene.**

The skew variant is annotated on the upright page while its capture is rotated by
three degrees, so scoring it against the upright annotation compared two frames.
`tools/metrics/de_ocr_qualification.dart` now derives the injected skew from the
variant's own raster record (`degradations: ["skew-3deg"]`, with
`evidence.skewDegrees` honoured when present) and rotates the annotation lines and
fields into the input-raster frame for that variant only, using the same mapping
as `make_variants.skew`. Re-scoring the unchanged c3 run files this way gives
**51/51 associated lines, CER 2.33 %, special-character recall 92.31 %, PASS** for
`scan-200dpi-skew-3deg`. The comparison with the reference capture is precise, not
an equivalence claim: association 51/51 = 51/51 and CER 2.33 % = 2.33 % match,
while special recall is 92.31 % vs 93.27 %, exact lines 38 vs 39, substitutions
20 vs 18, insertions 2 vs 4 and critical non-exact lines 8 vs 5. The six upright
variants keep their exact previous numbers because their annotation is not
transformed. The upright-annotation score of the same run (43.51 %, 30/51) is
retained only as the explicitly non-comparable measurement.

The transform cannot be faked: the new Python test
`test_skew_transform_is_frame_correct_and_sensitive` asserts that no transform
(`--gt-skew-degrees 0`), the wrong sign (`-3`) and a doubled angle (`6`) all lose
association, and the second new test
`test_label_normalization_guard_fires_at_200_dpi` is the positive control for the
anti-normalization guard (a relabelled 200 DPI suggestion must still produce the
verbatim FAIL reason and `nonVerbatimLabels = 1`), so the guard cannot silently
stop firing. All 12 scorer tests pass.
