German reference fixture and its pre-declared ground truth, the three separate
metric families and their scorer, the NFC/NFD regression fix in the production
label matcher, and the tooling corrections that made the pre-declared Android run

## 5. Results

**Delivered (host-verifiable).**

- Additive fixture `sf-005` (`fixtures-1.1.0`, 2 pages) written by a
  deterministic PDF 1.7 Type0/`CIDFontType2` writer that embeds the
  project-bundled Noto Sans Regular verbatim and resolves every printed code
  point through the font's own `cmap`, so U+1E9E (ẞ), `€`, `²` and `³` are
  proven covered rather than assumed. The generator's `--check` verifies 37
  generated files byte-for-byte; pinned `sf-001` and `sf-004` bytes are
  unchanged.
- Pre-declared ground truth (`lines[51]`, `critical` flags, `fields[13]`,
  `requiredCharacters[11]`, `requiredAuthorityTerms[8]`, `metricsPolicy`,
  `variants[7]`) generated from the same declaration as the PDF, so text and
  annotation cannot drift. `verify.sh` checks the pin, font coverage, structure,
  and the text-layer code points.
- Three separate metric families with no composite headline: raw OCR character
  fidelity (no normalization, geometry-associated lines, CER over the full
  alignment), Unicode representation findings (NFC/NFD, combining marks, missing
  umlaut dots, `ß`→`B`, ASCII folds), and semantic label/type assignment over
  production suggestions with `IoU ≥ 0.5`.
- Text-layer control: `TEXT_LAYER` `PASS` at CER 0.00 % (2/2 pages, 0
  missing/extra code points). This is a control path, never OCR evidence.
- Defect and regression: `TypeInference._normalizeForMatching` folded
  precomposed umlauts but not NFD spellings, so decomposed OCR output lost the
  `Geschäftszeichen` lexeme match. RED was recorded on the unmodified
  implementation (2 of 5 new tests failed), then GREEN after folding
  `base + U+0308` for a/o/u and their capitals and comparing a German-composed
  form for the literal-spelling preference. Non-German combining marks are left
  untouched, so they break the match instead of being silently repaired, and the
  raw `labelText` is never rewritten.

**Correction-1 — proven OCR quality defect and its fix (host-verified).**

*Root cause (label/type association).* `TypeInference` treated a printed label as
credible only inside a 24 pt Euclidean gap. The reference form, like an ordinary
authority form, prints each field label in a left column and the input region in
a second column, so the real label-to-field gap is 14–90 pt and grows with the
label's own length. On the reference variant that left 9 of 13 fields without
any label, gave the remaining ones the nearest heading or printed mask instead
of their label, and forced 12 of 13 suggestions to `multiline`: label accuracy
0.00 %, 8 unresolved labels.

*Fix (production, minimal).* `packages/feldexa_recognition/lib/src/type_inference.dart`
now associates a label printed on the candidate's own row (overlapping vertical
spans, and not printed mostly inside the candidate region) and ranks a same-row
label above a nearer line above or below. This is the documented cue semantics of
`ocr_alignment_right`; the 24 pt radius still governs all off-row labels, so the
proximity contract for headings and neighbouring rows is unchanged. No threshold,
golden datum, ground truth, expected text, or threshold value was touched, and no
recognized character is substituted, normalized, or rewritten.

*RED/GREEN (check 12 → checks 6/13).* Three new tests in
`packages/feldexa_recognition/test/type_inference_test.dart` pin the defect and
fail at the pre-fix bytes of `type_inference.dart` (commit `40a4260`):

- `a left label on the same row is associated beyond 24 pt`
- `a same-row left label wins over a heading line above`
- `a printed mask inside the candidate is not the structural label`

RED: 55 passed, 3 failed (exit 1). GREEN after the fix: 58 passed, 0 failed
(exit 0). Three pre-existing T053 tests were updated because they pinned the old
fixed-radius outcome for same-row labels (the boundary and tie-break cases now use
off-row positions, where the 24 pt rule still applies); one guardrail test
(`a label two rows above is still not a same-row label`) passes before and after
and prevents over-acceptance. Post-fix file hashes: `type_inference.dart`
`a2757ea0f6f972425d631b95966ca555869ec403693bad57c098e8b82566e367`,
`type_inference_test.dart`
`2ef4975a8325cdb3c9246dee5e32cf319c2adee67946f010da0b0e7aa4f16e53`.

*Not fixed, with reasons.* The special-character losses (`ß`/`ẞ`→`B`, `m³`→`m²`,
`§`→`S`, ASCII-folded punctuation) are limitations of the bundled ML Kit Latin
model; removing them needs a different engine or character-substitution
post-processing, both forbidden here, so they stay `FAIL`. The 3° skew variant
stays `FAIL` because the pipeline has no deskew stage; a deskew draft was
reverted unverified (its host JVM test gate could not be executed), so no
unverified production change was shipped.

*Post-fix emulator rerun.* `NOT_RUN`. The driver's mandatory Orca allocation gate
(`orca emulator devices --json`) stopped answering (`runtime_timeout`, then no
response), and the driver aborted before any device command
(`orca emulator devices --json failed; no Orca allocation evidence`). There is
therefore no post-fix on-device measurement; the class-run numbers at commit
`40a4260` remain the current runtime evidence.

**Correction-2 — the 3° skew defect (verified, measured on device).**

*Root cause.* The pipeline had no deskew stage: the injected 3° raster reached
the recognizer tilted, so lines merged or disappeared (30/51 associated) and the
returned boxes were too tall and too far from the annotated rows.

*Fix (production, minimal).* A new pure-math stage
`SkewCorrection.kt` estimates the dominant row skew with a projection-profile
search (±5°, 0.25° steps over ink-thresholded, subsampled luminance), rotates the
raster upright with bilinear sampling on a white background, and maps the
recognizer's rectangles back into the original raster frame;
`MlKitTextRecognizer.recognize` applies it before ML Kit. A raster whose estimate
is below 1.0° is passed through untouched, which is why every upright variant
keeps its exact pre-fix values. No recognized text is read, rewritten or
substituted.

*RED/GREEN (checks 14/15).* At the pre-fix baseline `correctionFor` returned no
correction and exactly the three deskew/symmetry tests failed (the three no-op
and identity tests passed): `./gradlew --no-daemon …` exit 1. After the fix the
same command over `SkewCorrectionTest` and `MlKitOcrServiceTest` is
`BUILD SUCCESSFUL` (exit 0). The Gradle daemon was stopped after the run.

*Measured effect (class-run report §5.8).* `scan-200dpi-skew-3deg` moves from CER
48.48 % / special recall 68.27 % / type accuracy 0.00 % (FAIL) to CER 15.42 % /
87.50 % / 100.00 % (PASS) with the pre-declared thresholds unchanged, and the six
other variants keep their exact pre-fix character metrics. The correction-1
label/type fix is now measured on device as well: label accuracy 0.00 % → 69.23 %
on the clean variants, 7.69 % → 84.62 % on the degraded ones, unresolved labels
8 → 1.

*Driver pull correction.* The correction-1 tar-based run-file pull produced a
non-tar stream (`exec-out` output was not a valid archive) and the first
correction-2 attempt lost its run files to the runner's uninstall. The driver now
pulls both files with `adb exec-out run-as cat`, verifies each as non-empty JSON
before scoring, and retries up to ten times; the successful attempt is recorded in
the class-run evidence.

**Not delivered here.** The runtime half of T263 is reported separately and is
`FAIL` against the pre-declared thresholds (reference variant CER 2.33 %,

in the OCR or analysis pipeline was repaired by T263: the qualification
