### Conformance expectation model

Each expectation declares exactly one state per adapter:

- `satisfied` — the check runs and any violation throws
  `ImportConformanceFailure`, which fails the runner.
- `notCovered` — the runner skips the check with a mandatory reason; it is never
  a pass and never counted as protection.
- `nonConforming` — the runner registers a deliberate failure; it can never be
  reported as a pass.

The T028 declaration covers 13 of 19 expectations:

`single-page-text-import`, `five-page-geometry-import`,
`source-immutability-and-verification`, `verify-detects-staged-corruption`,
`evidence-labelled-simulated`, `imp001-password-protected`,
`imp002-truncated-input`, `imp004-not-pdf`, `imp005-unknown-reason`,
`imp007-too-large`, `imp000-cancelled`, `save001-storage-full`, and
`no-record-after-rejection`.

These 6 expectations are **NOT COVERED** by T028 and are skipped in the runner
output with these reasons:

### `messageKey` contract drift and correction

`contracts/ports.md` §3 defines `messageKey` as the ARB key resolved to German
at the UI boundary, and `contracts/error-catalog.de.md` §11.1 maps a catalog
code to a lower-case key without the hyphen (`IMP-001` → `imp001`). The
committed `apps/feldexa_app/lib/l10n/app_de.arb` already contains `imp001`
through `imp007`, `save001`, `save003`, and the other mapped keys. The previous
implementation set `messageKey` to the catalog code (for example `'IMP-001'`).
The contract wins: `_arbMessageKey` now derives
`code.toLowerCase().replaceAll('-', '')` for rows that have a German ARB entry.

Catalog rows that deliberately have no committed German ARB entry keep the
stable code as `messageKey`:

| `SIM-001` | Developer-only code, never shown to a user. |

| `PLT-002` | Developer-only code, never shown to a user. |

### T028 staged-integrity blocker and smallest alternative

`packages/feldexa_adapters_simulated/lib/src/simulated_import_adapter.dart:177-182`
contains the read-back branch:

```text
if (readBack == null || length mismatch || sha256 mismatch) {
  backend.removeSourceIfUnreferenced(sourceId);
  throw ImportRejectedException(ImportRejectionKind.unreadable);
}
```

`contracts/storage-format.md` §3.1 step 3 and §5 require
`CorruptDataException` (`SAVE-003`) for a staged hash/authentication mismatch;
`IMP-002` is for unreadable input. The adapter is outside the authorised write
scope and `SimulatedBackend` exposes no way to corrupt a source between staging
and read-back. The smallest honest alternative implemented here is:

1. The reusable suite owns the exact `CorruptDataException` assertion
   (`packages/feldexa_testkit/lib/src/import_conformance_suite.dart:807`).
2. The T028 runner declares that expectation `notCovered` with the known
   non-conformance and the blocker reason
   (`packages/feldexa_adapters_simulated/test/import_conformance_test.dart:69`).
3. A separate covered expectation writes real corruption into the staged bytes
   after import and proves `verifySource` detects it
   (`.../import_conformance_test.dart:256`).

The minimal closing change for T028 would be one line at
`simulated_import_adapter.dart:182`: throw `CorruptDataException()` instead of
`ImportRejectedException(ImportRejectionKind.unreadable)`, plus an adapter test
that injects the read-back mismatch. That edit is not made here because the
adapter is outside the authorised scope.
