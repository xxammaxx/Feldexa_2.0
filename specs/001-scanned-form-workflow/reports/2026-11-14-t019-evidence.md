## 5. What the T019 rules guarantee

### 5.1 Normative matrix

`reclassifyField` implements the `data-model.md` §3.5 matrix and a documented
fallback for every remaining ordered pair:

- `text → multiline` preserves text, overflow metadata, and unknown JSON
  extensions.
- `multiline → text` joins each line break with one space only after explicit
  confirmation. Without confirmation the original multiline text is preserved
  as `IncompatibleValue` and flagged; the proposed joined `TextValue` is
  available for the explicit user action.
- `text/multiline → number/date` parses the documented German or canonical form.
  A compatible value is converted; a failure is preserved verbatim and flagged.
- `number/date → text/multiline` preserves `rawGerman`/canonical display text and
  clears a previous field error.
- `text/multiline/number/date → checkbox` preserves non-empty content as
  incompatible content and proposes an unchecked `CheckboxValue`; export is
  blocked until the user resolves the warning. Empty content becomes no value.
- `text/multiline/number/date → signature` preserves non-empty content as
  incompatible content; empty content becomes an unsigned signature.
- `checkbox → signature` clears the checkbox state as the data model requires.
  `checkbox → text/multiline` preserves a `Ja`/`Nein` display projection;
  `checkbox → number/date` preserves the projection without inventing a numeric
  or date interpretation.
- `signature → non-signature` clears the signature reference, surfaces the asset
  id for the §3.7 cleanup after the next verified commit, and fabricates no
  text.
- Same-type calls are no-ops and return the input field and value unchanged.

Empty text is treated as no content only for number, date, checkbox, and
signature targets. An empty value stays an empty value for text/multiline
targets, so presence is not silently changed.

### 5.2 Persisted warning and surfaced error

`data-model.md` §3.5 says unparseable text moved to number/date is "marked
error". The T017 aggregate, the T020 `RevisionContent`, and
`ConfirmedField.acceptsValue` require every persisted `IncompatibleValue` to be
paired with a `FieldValidation.warning` carrying
`WarningCode.incompatibleContent`; an error state cannot accompany preserved
content. T019 therefore persists the aggregate-valid pair
(`IncompatibleValue` + `FLD-002`) and exposes the parse failure separately as
`ReclassificationResult.errorCode` (`NUM-001`, `DATE-001`, or `DATE-002`). This
is tested directly, including a real `Document` built from each result. The
content stays in the model, the error reaches the UI, and export stays blocked,
which is the FR-038 requirement the aggregate can represent.

### 5.3 Parsing

The parsers are small, pure, and documented rather than a second input-control
implementation:

- Numbers accept canonical `-?\d+(\.\d+)?`, German comma decimals, and valid
  German grouping. A valid grouping wins over a canonical dot decimal, so the
  German display `1.234` becomes `1234`; `rawGerman` retains the exact entered
  text.
- Dates accept German `d.m.yyyy` with one or two day/month digits and a
  four-digit year, plus the canonical `yyyy-mm-dd` emitted by date → text.
  Structurally valid non-existent dates are `DATE-002`; other failures are
  `DATE-001`. Leap days are validated.
- Trimming applies to parsing only. Preserved content keeps the exact entered
  text, including German characters, umlauts, spaces, and line breaks.

### 5.4 Resolution, warnings, and no silent deletion

`ReclassificationResult.resolve` is the only content-discarding path: it
replaces preserved content with the proposed value, or with no value when
resolution means leaving a number/date/signature without content. It is
explicit, idempotent, and never invoked automatically by `reclassifyField`.
Warnings never delete or truncate content. `resolve` clears the warning and
`errorCode` because the user has acted. A same-type call preserves an existing
warning unchanged.

### 5.5 Aggregate compatibility and limits

Every result is accepted by the T017 aggregate: a stored value matches the field
type or is an `IncompatibleValue` paired with the warning, and a signature value
is paired with a matching `SignatureMark`. The tests build a real `Document` for
each of the 6 × 6 ordered pairs and for every explicit outcome. Overflow
metadata and a known overflow warning survive a compatible conversion; the
`incompatible_content` warning takes precedence when content must be preserved.

`NumberValue.rawGerman` is display text and is not length-limited by T018. A
valid number value can therefore carry more than 10,000 characters, while every
persisted target value is limited to 10,000. Truncating would violate FR-038, so
the conversion fails with a constant `ArgumentError` that never echoes content;
this limit is documented and tested.

### 5.6 Privacy and ownership

Errors and `ReclassificationResult.toString` never echo labels, text, dates,
numbers, or preserved content. The result exposes `preservedContent` explicitly
and documents it as sensitive. T019 adds no new canonical type, no second
`FieldValue`, and no duplicate of a T017/T018/T020/T021 type.

## 7. Limitations

- This is host-VM and static-analysis evidence only (`NONE`). It cannot prove
  Android runtime behavior, touch/keyboard UX, filling controls, persistence
  encryption, export, or device acceptance.
- The module is the pure compatibility layer. Wiring the rules into the T066
  reclassify command, the review UI, undo/redo, and the choice between
  `resolve` and user-entered replacement values belongs to later tasks.
- `data-model.md` §3.5's "marked error" for unparseable number/date content is
  represented as the aggregate-valid `incompatible_content` warning plus the
  surfaced `NUM-001`/`DATE-001`/`DATE-002` code, not as
  `FieldValidation.error`, because the T017/T020 aggregate rejects an error
  state paired with preserved content. This reconciliation is documented in the
  module and tested.
- A `NumberValue` whose unbounded `rawGerman` display text exceeds 10,000
  characters cannot be converted losslessly to any persisted target variant and
  fails with a constant error instead of truncating. This case is expected to be
  unreachable through the filling controls but is handled defensively.
- The pre-existing `gradlew.bat` modification remains uncommitted and is not
  covered by any T019 claim.
