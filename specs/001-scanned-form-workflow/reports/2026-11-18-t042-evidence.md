## 1. Scope

This report covers exactly T042 / issue #42: the pdfrx page viewer and the
source-point geometry mapping in
`apps/feldexa_app/lib/features/editor/page_view.dart`, plus its host-VM /
widget test. The implementation adds two committed Dart files and changes no

What this run proves:

- A `PageView` widget opens the protected source bytes exactly once per opaque
  source id through an injected `PageViewSourceBytes` provider, creates one
  renderer/document object per source, and reuses it across rebuilds. The
  production renderer is pdfrx/PDFium (`openPdfrxPageRenderer`,
  `PdfPageView`); a fake renderer seam is used only for host-VM tests.
- Every page is placed in original document order using only
  `PageGeometry.displaySize` as geometry input. The widget test renders three
  pages at their expected view sizes, including a rotation-90 page whose
  display width and height are swapped.
- Pages are built lazily: only pages intersecting the viewport plus a
  64-content-point overscan are instantiated, so a 100-page document does not
  allocate 100 page renderers at once.
- The view transform is exactly the contract's section 3 formula
  `view = pan + scale × content`, with one uniform `scale` and one `pan`.
  `view ↔ display` round-trips at scales `0.5`, `1`, `1.75`, `3`, and `8`.
- Display points map to the same PDF point at every tested zoom level; the
  page display → PDF conversion is delegated to the canonical
  `PageGeometry.displayToPdf` and is not reimplemented here.
- Rotation `0/90/180/270` combined with a non-zero CropBox offset
  `(10, 20, 550, 770)` produces the expected display sizes and PDF points:
  display `(37, 59)` maps to PDF `(47, 731)`, `(69, 57)`, `(523, 79)`, and
  `(501, 753)` respectively.
- A display rectangle round-trips through the view without changing its PDF
  geometry; a zoomed viewport does not alter the model rectangle.
- Device pixel ratio is not an input to any geometry method. A widget test
  changes DPR from `1` to `3` while holding the logical viewport constant; the
  controller scale, pan, and page mapping are unchanged.
- The hit-testing API converts a viewport offset plus page index to a display
  point and rectangle, and back, and exposes the page index under a pointer.
  All return values are documented as page display space (PDF points, top-left
  origin, y down) or view space (logical pixels) by method name.
- Source bytes are never written to a file or cache by this file, and no log
  entry contains a source id, path, URI, title, page content, or raw renderer
  error. `PageViewLoadException` carries only a stable failure enum.
- The renderer is disposed on source change and widget removal; a page-count
  mismatch refuses to paint pages and disposes the opened renderer.

### Geometry mapping design

| Space | Definition in T042 |
| --- | --- |
| Page display space | PDF points, top-left of the visible page box after `/Rotate`, y down. The page size is `PageGeometry.displaySize`, read exactly once in `PageViewController.fromImportedSource`; rotation and CropBox intersection are already encoded there. |
| Content space | Page display points translated by the page's vertical strip position, before zoom. `PageViewLayout` stacks pages in original order, centers narrower pages, and inserts an 8-point UI gap. It is derived UI state and is never persisted. |
| View space | Flutter logical pixels, top-left viewport origin. `view = pan + scale × content`, exactly `contracts/coordinates-and-geometry.md` §3. |
| PDF user space | PDF points, bottom-left, y up. T042 does not duplicate the formula: a caller passes the display point from `viewToDisplay` to the page's canonical `PageGeometry.displayToPdf`. |

The transform inputs are only:

- `PageGeometry.displaySize` per page, through `fromImportedSource`, or a
  pre-derived `PageViewPageSize` for tests and a future `Document` caller;
- `PageViewController.scale`, the logical pixels per PDF point;
- `PageViewController.pan`, the view-space translation of the content origin.

There is no device-pixel-ratio, raster-size, pdfrx page-width, device-pixel, or
normalized-fraction input. `fitWidthScale` is
`viewportWidth / widestDisplayWidth`; `minScale = 0.5 × fitWidthScale`;
`maxScale = 8 × fitWidthScale`. `view ↔ display` round-trips within `1e-9`,
and the same display point maps to the same PDF point at every tested scale.

`PageViewController` exposes the hit-testing API:
`viewToDisplay(pageIndex, viewportOffset)`,
`displayToView(pageIndex, displayPoint)`,
`viewRectToDisplay(pageIndex, viewportRect)`,
`displayRectToView(pageIndex, displayRect)`, and
`pageIndexAt(viewportOffset)`. Every returned display value is documented as
PDF points with the top-left display origin; view values are logical pixels.
The overlay editor and T043 page strip can share the same controller.

### Page rendering and lifecycle

- `PageView` treats the opaque `sourceId` as the document identity. It calls
  `sourceBytes` once when that id is first shown, creates one renderer through
  `rendererFactory`, and does not re-open when the widget rebuilds or when a
  parent supplies a new provider closure for the same id. A test rebuilds with
  a new closure three times and observes one source call and one document.
- The renderer's `pageCount` must equal the controller's page count; otherwise
  the renderer is disposed and the viewer shows its error placeholder without
  painting pages. This prevents page geometry from one document being applied
  to another.
- Only pages overlapping the visible content plus 64 content points are
  instantiated. The widget test starts at fit-width with only page 0 built and
  `scrollToPage(2)` removes page 0 and builds page 2.
- The renderer is disposed on source change and on viewer removal. The widget
  test observes the old renderer disposed after a source change and the single
  renderer disposed after unmounting.
- `PdfPageView` paints the unchanged original page inside the page's display
  box. The production renderer uses `maximumDpi: 300` and a white page
  decoration; it never rewrites, re-lays-out, OCR-reconstructs, or crops the
  page to a smaller box.

### Cached data and location

- `PageView` state holds only the renderer handle, controller reference, and a
  sanitized load state. It does not retain the source byte reference after
  handing it to the renderer.
- pdfrx/PDFium keeps one open `PdfDocument` in process memory per source. For
  documents at or below pdfrx's 1 MiB in-memory threshold, PDFium holds a
  native copy; larger documents use a memory-backed `PdfiumFileAccess` read
  callback that retains the decrypted Dart byte buffer until
  `PdfDocument.dispose`. This is process memory, not a file.
- Each built `PdfPageView` holds its rendered `ui.Image` until the page leaves
  the viewport or the viewer is disposed. Only visible/overscan pages have
  images.
- No temporary file, on-disk cache, thumbnail, document path, URI, title, or
  page content is written or logged by T042. pdfrx's file-based HTTP cache is
  not used by `openData`; the neutral `feldexa-viewer-<n>` source name contains
  no document identity.

### Privacy and failures

`PageViewSourceBytes` is the only source seam; the viewer never accepts a path
or URI. A `null` or empty result is `sourceUnavailable`; a renderer exception
is reduced to `unreadableSource`; a page-count mismatch is
`pageCountMismatch`. `PageViewLoadException.toString()` contains only the enum,
and tests assert that neither a source id nor a synthetic absolute path
appears in the reported failure. The viewer adds no logging and no error text;
a later task can map the stable failure to German UI text.

- Plaintext zeroization is not guaranteed. The viewer releases its own byte
  reference, but pdfrx/PDFium may retain the document bytes and rendered page
  images in process memory until disposal; garbage collection and native
  allocator behavior are outside this file's control. No disk cache is
