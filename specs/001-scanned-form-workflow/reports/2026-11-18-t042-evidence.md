### Geometry mapping design

| Space | Definition in T042 |
| --- | --- |
| Page display space | PDF points, top-left of the visible page box after `/Rotate`, y down. The page size is `PageGeometry.displaySize`, read exactly once in `PageViewController.fromImportedSource`; rotation and CropBox intersection are already encoded there. |
| Content space | Page display points translated by the page's vertical strip position, before zoom. `PageViewLayout` stacks pages in original order, centers narrower pages, and inserts an 8-point UI gap. It is derived UI state and is never persisted. |
| View space | Flutter logical pixels, top-left viewport origin. `view = pan + scale × content`, exactly `contracts/coordinates-and-geometry.md` §3. |
| PDF user space | PDF points, bottom-left, y up. T042 does not duplicate the formula: a caller passes the display point from `viewToDisplay` to the page's canonical `PageGeometry.displayToPdf`. |

The transform inputs are only:

- `PageGeometry.displaySize` per page, through `fromImportedSource`, or a
  pre-derived `PageViewPageSize` for tests and a future `Document` caller;
- `PageViewController.scale`, the logical pixels per PDF point;
- `PageViewController.pan`, the view-space translation of the content origin.

There is no device-pixel-ratio, raster-size, pdfrx page-width, device-pixel, or
normalized-fraction input. `fitWidthScale` is
`viewportWidth / widestDisplayWidth`; `minScale = 0.5 × fitWidthScale`;
`maxScale = 8 × fitWidthScale`. `view ↔ display` round-trips within `1e-9`,
and the same display point maps to the same PDF point at every tested scale.

`PageViewController` exposes the hit-testing API:
`viewToDisplay(pageIndex, viewportOffset)`,
`displayToView(pageIndex, displayPoint)`,
`viewRectToDisplay(pageIndex, viewportRect)`,
`displayRectToView(pageIndex, displayRect)`, and
`pageIndexAt(viewportOffset)`. Every returned display value is documented as
PDF points with the top-left display origin; view values are logical pixels.
The overlay editor and T043 page strip can share the same controller.

### Page rendering and lifecycle

- `PageView` treats the opaque `sourceId` as the document identity. It calls
  `sourceBytes` once when that id is first shown, creates one renderer through
  `rendererFactory`, and does not re-open when the widget rebuilds or when a
  parent supplies a new provider closure for the same id. A test rebuilds with
  a new closure three times and observes one source call and one document.
- The renderer's `pageCount` must equal the controller's page count; otherwise
  the renderer is disposed and the viewer shows its error placeholder without
  painting pages. This prevents page geometry from one document being applied
  to another.
- Only pages overlapping the visible content plus 64 content points are
  instantiated. The widget test starts at fit-width with only page 0 built and
  `scrollToPage(2)` removes page 0 and builds page 2.
- The renderer is disposed on source change and on viewer removal. The widget
  test observes the old renderer disposed after a source change and the single
  renderer disposed after unmounting.
- The custom `_PdfrxPage` widget paints the unchanged original page inside the
  page's display box. It calls `PdfPage.renderForDisplay` directly with a
  cancellation token and `pixelSizeThreshold`; its raster dimensions come from
  `PageViewRasterPlan.forPage` (300 DPI limit, device pixel ratio, 4096-pixel
  long-edge cap, and the `1 / max(pageWidthPt, pageHeightPt)` positive floor),
  not from a `maximumDpi` widget property. It never rewrites, re-lays-out,
  OCR-reconstructs, or crops the page to a smaller box.

### Cached data and location

- `PageView` state holds only the renderer handle, controller reference, and a
  sanitized load state. It does not retain the source byte reference after
  handing it to the renderer.
- pdfrx/PDFium keeps one open `PdfDocument` in process memory per source. For
  documents at or below pdfrx's 1 MiB in-memory threshold, PDFium holds a
  native copy; larger documents use a memory-backed `PdfiumFileAccess` read
  callback that retains the decrypted Dart byte buffer until
  `PdfDocument.dispose`. This is process memory, not a file.
- Each built `_PdfrxPage` state holds its rendered `ui.Image` until the image
  is replaced, the page leaves the viewport, or the viewer is disposed; the old
  image is disposed on replacement and in `dispose`. Only visible/overscan
  pages have images.
- No temporary file, on-disk cache, thumbnail, document path, URI, title, or
  page content is written or logged by T042. pdfrx's file-based HTTP cache is
  not used by `openData`; the neutral `feldexa-viewer-<n>` source name contains
  no document identity.

### Privacy and failures

`PageViewSourceBytes` is the only source seam; the viewer never accepts a path
or URI. A `null` or empty result is `sourceUnavailable`; a renderer exception
is reduced to `unreadableSource`; a page-count mismatch is
`pageCountMismatch`. `PageViewLoadException.toString()` contains only the enum,
and tests assert that neither a source id nor a synthetic absolute path
appears in the reported failure. The viewer adds no logging and no error text;
a later task can map the stable failure to German UI text.

### 5.1 Review-correction round 1

The independent reviews at `a28fbf0` failed the candidate on three blocking
findings and one low hardening finding. The correction commit
`605344504eb87466a8c278bb19af0364b70c9e01` addresses all four.

- **4096-pixel long-edge cap.** `PageViewRasterPlan.forPage` computes
  `logicalScale = viewWidth / pageWidthPt`, `desiredScale = logicalScale × DPR`,
  then `effectiveScale = min(desiredScale, 300/72, 4096 / max(pageWidthPt, pageHeightPt))`.
  Raster dimensions are `round(pageSizePt × effectiveScale)` clamped to
  `[1, 4096]`. The painter uses only the plan; `PageViewController.scale`,
  `pan`, page boxes, and `view ↔ display` mapping are untouched. The A3 test
  (`842 × 1191 pt`, 8× view, DPR 3) asserts a 4096-pixel long edge and
  `isCapped`; a 100 × 150 pt page at DPR 2 remains 400 × 600; a mapping captured
  before the plan is byte-for-byte equal after it.
- **Fit-width target-scale clamp.** `fitWidth()` now computes
  `targetScale = fitWidthScale` and clamps `Offset.zero` with
  `_clampPanFor(Offset.zero, targetScale)` before committing. The
  **discriminating regression is the zoom-out case**: page `100 × 100 pt`,
  viewport `200 × 200`, `setView(scale: 1, pan: Offset.zero)`, then
  `fitWidth()`; it asserts scale `2`, pan `(0, 0)`, and page rect
  `(0, 0, 200, 200)`. On `a28fbf0` the old clamp ran at scale 1, where the
  content is smaller than the viewport and returns the centering offset
  `(50, 50)`; applying scale 2 then clipped the page with `left == 50`. The
  retained zoom-in test (`scale 4`, pan `(-150, -150)`) is explicitly named a
  non-discriminating sanity check: it passes before and after because the old
  clamp's "content larger" branch returns `(0, 0)`, so it is not RED evidence.
- **Render-error containment.** The production renderer no longer uses
  `PdfPageView`, whose pinned 2.12.0 implementation logs `Error creating image:
  $e` through `developer.log` and never reaches `onLoadError`. The new
  `_PdfrxPage` widget computes the raster plan, calls
  `PdfPage.renderForDisplay` directly with a cancellation token and the

### 5.4 Consolidated correction round and real RED transcript

The consolidated round enforced the public cap, defined a minimum page extent,
and closed the far-edge and point-subtraction checks.

- **Public cap policy — reject above 4096.** `PageViewRasterPlan.forPage`
  now throws for `maxLongEdgePx < 1 || maxLongEdgePx > maximumRasterLongEdgePx`

  the default remains 4096. This is a public, documented policy rather than
  trusting every caller.
- **Minimum page extent — 0.001 pt.** `PageViewPageSize` rejects any width or
  height below `minimumPageExtentPt = 0.001`. The rationale is the same
  three-decimal quantum used by persisted `Rect` serialization; it is far below
  any real page, rejects `1e-320` degenerate sizes whose reciprocal overflows,
  and keeps `1 / max(widthPt, heightPt)` finite (at most 1000). The smallest
  permitted `0.001 × 0.001 pt` page produces a finite positive plan within
  the caps.
- **Far-edge and point guards.** `pageRectInViewport` checks
  `right = left + width` and `bottom = top + height`; `viewToDisplay` checks its
  page-origin subtraction; `displayToView` checks its sum before the transform.

  the production path.

## 7. Limitations

- `NONE` is not a runtime evidence class. No Android runtime, emulator,
  device, PDFium execution, SAF picker, protected store, Keystore, browser,
  OCR, field detection, export, or user journey was executed.
- The production `openPdfrxPageRenderer` path was analyzed and compiled but
  not run. The host-VM widget test uses a fake `PageViewRenderer`; it proves
  page order, sizes, lazy building, lifecycle, and mapping, not PDFium output.
- No page pixels, visual fidelity, crop correctness, on-screen orientation, or
  rendering quality was compared against a PDF viewer or printer. A pdfrx page
  aspect that disagrees with `PageGeometry.displaySize` would be stretched or
  distorted into the computed display box by `RawImage(fit: BoxFit.fill)`, not
  letterboxed; geometry remains authoritative, but visual equivalence is
  unverified.
- Pinch and drag gesture handling is analyzed and uses the controller's
  transform, but no pointer-simulation test exercises the actual gesture path.
  The controller transform, fit width, fit page, scroll-to-page, and hit
  testing are tested directly.
- `PageView` is not wired into a route or a document model. The current
  production geometry path is `PageViewController.fromImportedSource`, which
  accepts an `ImportedSource`; a later editor that starts from `Document`
  must map each `Page.geometry.displaySize` to `PageViewPageSize`. The app
  currently declares `feldexa_core` as a dev dependency only; T042 deliberately
  does not change `pubspec.yaml`/`pubspec.lock`, so it avoids importing core
  into `lib/` and keeps the PDF formula in `PageGeometry`. Promoting core to a
  runtime dependency, or providing a core-backed factory, is a follow-up
  integration concern.
- The viewer has one display size per page. T044 must define behavior for
  partially unreadable pages and the `IMP-006` warning; T042 does not invent
  a placeholder geometry.
- Plaintext zeroization is not guaranteed. The viewer releases its own byte
  reference, but pdfrx/PDFium may retain the document bytes and rendered page
  images in process memory until disposal; garbage collection and native
  allocator behavior are outside this file's control. No disk cache is
  created, but pdfrx's own diagnostics were not inspected under logcat.
- No release build, R8/minify run, APK install, or performance measurement was
  performed. No `3 s` or frame-budget claim is made.
- The pre-existing dirty `apps/feldexa_app/android/gradlew.bat` line-ending
  change remains in the worktree and is reported as dirty with its SHA-256; it
  is not a T042 artifact and was not staged or committed.
- `tasks.md` was not edited, so the T042 checkbox remains unchanged for the
  coordinator/integrator. The reviewer-owned `checklists/precision-testability.md`
  still has 36 unchecked items and was not modified.
- This report omits its own byte size and SHA-256, and the implementation and
  report commit object ids that would change them. Those values are recorded in
  the external attestation. Every other artifact row below has path, byte
  size, and SHA-256.
