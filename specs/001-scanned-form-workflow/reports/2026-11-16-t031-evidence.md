### 7.2 Amended contract text (quoted)

`contracts/storage-format.md` §4, added paragraph:

> **Execution order (normative).** Step 4 (the plaintext export-preview cleanup)
> executes **before** the native recovery steps 1–3 and 5–6. Within the native
> recovery, steps 1 → 2 → 3 → 5 → 6 keep exactly that order and step 6 remains
> last, so the effective startup order is 4 → 1 → 2 → 3 → 5 → 6.
>
> Justification: a stale export preview is decrypted plaintext in the app-private
> cache. It must be removed even when native recovery fails or times out, because
> a degraded startup must not leave plaintext behind. The existing native method
> is one call that performs steps 1–3 and 5–6 without a phase selector, so the
> only ordering that guarantees step 4 for every native outcome is to run step 4
> first. Step 4 is bounded and deletes only entries from the dedicated export
> directory; it never touches an aggregate, a KEK alias, a revision, or a source
> byte. Its failure is reported, never silently skipped.

`contracts/platform-channel.md` §4 store rule, amended sentence:

> `store.startupRecovery` is synchronous and exposes the T026 native recovery
> (stale `tmp/`, incomplete aggregates, head fallback, unreferenced signatures,
> orphan aliases) — that is, `storage-format.md` §4 native steps 1–3 and 5–6.
> Under the owner decision of 2026-11-17 the startup execution order is
> 4 → 1 → 2 → 3 → 5 → 6: T031 runs its Dart plaintext export-preview cleanup
> (step 4) first and then calls this one native method, which performs its own
> steps in the 1 → 2 → 3 → 5 → 6 order with step 6 last. T031 must not duplicate
> the native sweep in Dart. Step 4 is bounded, touches only the dedicated export
> directory (never an aggregate, KEK alias, revision, or source byte), and is not
> skipped when native recovery fails or times out.

## 9. Limitations and residual risks

- `NONE` host checks and the `EMULATOR` run are separate; no result is
  extrapolated from one class to another.
- The step-4 export pass is intentionally **not** interruptible: a timeout can
  return to the caller while that bounded pass finishes. It processes at most
  `maxEntriesPerCategory` (512) entries in one directory, and exceeding the
  bound is reported as degraded. This is the owner-decided trade-off.
- The native `store.startupRecovery` call remains monolithic and cannot be
  interrupted mid-call; work inside it completes even after a timeout. All
  non-export work after it stops at the next checkpoint.
- On this device run only `SignatureSweepInstrumentedTest` (2 tests) executed by
  class filter; the other instrumentation classes were compiled but not run in
  this round.
- The integration test seeds `Directory.systemTemp/feldexa_exports`, which the
  Android Flutter runtime maps to the app-private cache; it exercises the
  production `StartupSweep` and `IoStartupSweepFileSystem`, but it does not
  simulate a full process restart or a real user export session.
- Instrumentation evidence covers the step-6 event and signature retention; it
  does not re-run the full store/channel matrix.
- No independent review has occurred. This is an author report and not an
  approval; the review table in §12 is blank.
- The first offline instrumentation attempt needed one non-offline dependency
  priming run (§5.2); this is tooling-only and does not weaken the app-level
  no-network property.
- The bare `orca-ide emulator kill --json` form returned `emulator_no_active`;
  the explicit device/worktree kill succeeded and the session list is empty.
