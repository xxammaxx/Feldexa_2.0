## 7. Finding detail

### 7.1 Finding 1 — exact `§4` order: blocked, not claimed fixed

Exact conflicting contract sentences (quoted verbatim):

- `specs/001-scanned-form-workflow/contracts/storage-format.md` **§4, line 201**:
  "On app start (before the list is shown), run in this order:" — followed by
  steps 1, 2, 3, then
  **line 210**: "4. Delete export artifacts older than 24 h and any on session
  end.",
  **line 211**: "5. Delete orphaned KEK aliases under `feldexa.doc.v1.` and
  `feldexa.tpl.v1.` that have no corresponding aggregate directory. Never
  delete an alias whose aggregate directory still exists.",
  **line 212**: "6. Write a redacted recovery event with counts only (including
  orphan aliases removed, but no IDs, titles, or content)."
- `specs/001-scanned-form-workflow/contracts/platform-channel.md` **§4, line
  215** fixes the method shape: `| store.startupRecovery | {} | { tempEntriesRemoved,
  incompleteAggregatesRemoved, unreadableAggregates, fallbackAdoptions,
  orphanAliasesRemoved, orphanAliasesRetained, orphanAliasesFailed,
  aliasSweepSkipped, ambiguousRevisionOrder, prunedRevisions } |`.
- `specs/001-scanned-form-workflow/contracts/platform-channel.md` **§4, line
  230**: "`store.startupRecovery` is synchronous and exposes the T026 native
  recovery (stale `tmp/`, incomplete aggregates, head fallback, unreferenced
  signatures, orphan aliases). T031 must call it before its Dart
  `StartupSweep.run()` and must not duplicate the native sweep in Dart."

Why a single monolithic `store.startupRecovery` cannot satisfy 1→2→3→4→5→6:

1. Steps 1–3 and 5–6 are one Kotlin call (`EncryptedStore.startupRecovery`,
   `apps/feldexa_app/android/.../EncryptedStore.kt:1079`); the request is `{}`,
   so the call cannot be told "stop after step 3".
2. There is no second native method that performs only steps 5–6: the §4 method
   table lists exactly `store.status`, `list`, `stageSource`,
   `createDocument`, `startupRecovery`, `readSource`, `readSignature`,
   `writeSignature`, `saveRevision`, `createTemplate`, `saveTemplateVersion`,
   `loadDocument`, `loadTemplate`, `delete`, `recoveryStamp`.
3. Calling `startupRecovery` twice does not help: the first call already runs
   steps 5–6 (alias sweep + event) before Dart can run step 4, so step 4 would
   again follow steps 5–6.
4. The two rules also contradict each other for a monolithic call: if the
   whole native call must happen "before its Dart `StartupSweep.run()`"
   (line 230), then step 4 is necessarily last (1→2→3→5→6→4), which violates
   `storage-format.md` §4's order; if step 4 goes first, the native call is no
   longer before `run()` and 4 precedes 1–3.

Attempted implementation and why it stops: the only exact-order design is
native(phase A: 1–3) → Dart(4) → native(phase B: 5–6). Both the phase selector
(a new request field) and the split method (a new/renamed channel method) are
explicitly excluded by the dispatch, so no contract file and no wire shape was
changed.

Residual deviation, stated honestly: production executes **4 → 1 → 2 → 3 → 5 →
6**. The Dart export-preview pass runs before the native call; native steps 1–3
and 5–6 then run in contract order relative to each other. This is a recorded
deviation, not exact fulfilment, and it is documented in
`startup_sweep.dart:519-560` and `EncryptedStore.kt:1062-1077`.

Minimal proposed amendment (**proposal only, not applied**):

> `platform-channel.md` §4: change the `store.startupRecovery` request from `{}`
> to `{ "phase": "recover" | "finalize" }`, where `recover` performs §4 steps
> 1–3 and `finalize` performs §4 steps 5–6; the response object stays unchanged
> for both phases. `storage-format.md` §4 gains one sentence: "The native
> recovery runs in two phases so step 4 can execute between native step 3 and
> native step 5."

A smaller alternative that is also acceptable from the app's side: keep one
method but make step 5–6 the responsibility of a second, explicitly named
method (for example `store.startupRecoveryFinalize` with request `{}`).

### 7.3 Finding 3 — post-timeout work is stopped and reported

- `startup_sweep_cancellation.dart` adds `StartupSweepCancellation`
  (`cancel()`, `isCancelled`).
- `runStartupSweepBounded(..., onTimeout: sweep.cancel)` requests the stop at the
  moment the bounded wait expires; `main()` passes `sweep.cancel`.
- `StartupSweep.run()` checkpoints: before the export pass, before the native
  call, before the staging pass, before each `list`, before each
  `recoveryStamp`, and before every individual deletion. A stopped run returns
  `StartupSweepStatus.degraded`, so it can never be read as success.
- Test (`startup_sweep_test.dart`, "a timed-out sweep performs no read or
  deletion after the stop"): a gated fake native recovery keeps the sweep
  running past the 10 ms bound; after the timeout the gate is released and the
  run finishes. Observed trace: `['export.list', 'native.start', 'native.end']`
  — no `temp.list`, `store.calls` is empty, `files.deletedTemporary` is empty,
  `result.status == degraded`. Additional tests pin "an already cancelled sweep
  reads and deletes nothing" and the production-shaped timeout path.
- Residual, stated explicitly: the single native `store.startupRecovery` call is
  monolithic and cannot be interrupted mid-call, so steps already inside that
  call complete. Everything after it (staging sweep, aggregate list/stamp reads,
  every deletion) is now provably stopped, and the degraded state is visible to
  the user (§7.2).

### 7.4 Finding 4 — session-end sweep has a production caller

- `session_end_sweep.dart` defines `SessionEndSweepBinding extends
  WidgetsBindingObserver` with `sessionEndStates = {paused, detached}` and calls
  `sweep.sweepSessionEnd()`. `inactive`/`hidden`/`resumed` deliberately do not
  sweep (`inactive` is transient focus loss).
- `main.dart` (`_FeldexaAppState`) registers the binding in `initState`, removes
  it in `dispose`, and re-registers only when the sweep instance changes.
- `main()` passes the same production sweep instance it just ran.
- Tests (`startup_wiring_test.dart`, group "session-end wiring") drive the real
  framework lifecycle (`tester.binding.handleAppLifecycleStateChanged`) against
  `FeldexaApp` and assert the export artifact is deleted on `paused` and on
  `detached`, is *not* deleted on `inactive`, and is not swept after the widget
  is disposed.
- The documented lifecycle point exists without a contract change: Flutter's
  own application lifecycle, plus `plan.md:60` ("Export preview files live only
  in app-private cache for the duration of the preview and are swept on
  startup/session end") and `storage-format.md:210` ("…and any on session end").
