## 1. Scope

This report covers exactly T040 / issue #40: the streaming encrypted source copy
and verified document commit in
`apps/feldexa_app/android/app/src/main/kotlin/de/feldexa/app/import/ImportService.kt`
and
`apps/feldexa_app/android/app/src/main/kotlin/de/feldexa/app/storage/EncryptedStore.kt`
(FR-004; FR-095/FR-096). The task makes the system's own protected copy the
document's source of truth and turns a staged aggregate into a listed document
only after preflight and a verified, atomic commit.

What this run proves:

- `EncryptedStore.stageSourceFromStream` reads the picked source in two bounded
  passes: a 64 KiB SHA-256/byte-count pass and a 1 MiB authenticated FXC1 write
  pass. It never materializes the whole source, never calls a whole-buffer API,
  and never creates a plaintext temporary file or plaintext copy.
- The staged source is read back chunk by chunk and verified against the
  streamed SHA-256 and byte count before any document can become visible. A
  mismatch (including a changed second pass or trailing bytes) fails closed and
  removes the incomplete aggregate.
- `EncryptedStore.openSourceReader` exposes a decrypting, seekable,
  chunk-bounded reader over the staged ciphertext. The production seam passes it
  to `PdfPreflight` through a `RandomAccessRead` adapter, so preflight never
  reads a plaintext file.
- After preflight succeeds, the initial revision and `meta.fx1`/`head.fx1` are
  committed exactly once. A duplicate visible aggregate is rejected without
  overwriting it; no second identity or initial revision is generated.
- `IMP-001`/`IMP-002`/`IMP-004`/`IMP-005` reject without a document, draft,
  template, or stored record. `IMP-006` succeeds with
  `pages[].unreadable = true`, `pageFailures`, and a persisted page failure.
- The committed document reads back through the protected store after the
  picked source is made unavailable; only `ContentResolver.openInputStream`
  (represented by the `PickedDocument` seam) is used, never a path conversion.
- Failure cleanup, cancellation, and the T038 lock-free repeated-cancel
  behaviour are preserved. A late cancellation after the verified commit does
  not delete the visible document.
- Review-correction round 1 (`cf3fe92`) removes the lifecycle-lock/handle-lock
  deadlock, owns the second provider stream immediately, and propagates
  aggregate/key cleanup failures instead of reporting a clean cancellation
  while encrypted residue may remain. The new interleaving tests cover
  cancellation during commit, a pre-first-chunk write failure, abort between
  chunks, abort after the last chunk but before promotion, abort at the last
  checkpoint before meta, and aggregate/key cleanup failures.
- The new Kotlin production code compiles into the debug Android app; the
  shared Dart layer analyzes with `flutter analyze --no-pub` and reports no
  issues (no Dart file was changed).

### 5.1 Review-correction round 1

The coordinator's Review A found three blocking findings on merged candidate
`78f5432`; all three were reproduced as RED on that tree before the fixes.

- **P1 deadlock — cancellation during commit.**
  `ImportService` called `context.cancellationCleanupFailure()` while holding
  the staged-lifecycle lock. The facade cleanup runs under the operation-handle
  lock and then waits for that lifecycle lock, so the two paths formed an ABBA
  deadlock. The deterministic RED test latches the commit, claims cancellation,
  releases the commit, and expects `PLT-004`:
  `cancellationDuringCommitDoesNotDeadlockAndReportsPlt004` failed on
  `78f5432` with
  `java.lang.AssertionError: worker did not finish; cancellation/commit deadlocked`.
  The fix replaces the in-lock handle read with a private
  `CommitCancelledException` marker; the outer catch reads
  `cancellationCleanupFailure` only after the lifecycle lock is released.
- **P2 stream ownership — second provider stream.** `openStreamForWrite()` was
  opened before `writeContainer`'s `use`. `stageSourceFromStream` now wraps the
  opened stream in `writePass.use { … }` immediately. The RED test injects a
  `STAGE_CREATE` failure and uses a close-tracking `InputStream`:
  `writeFailureBeforeTheFirstChunkClosesTheProviderStreamAndReportsResidue`
  failed on `78f5432` with
  `java.lang.AssertionError: the provider write stream must be closed`; it now
  passes and also asserts the reported `SAVE-003` residue state.
- **P2 cleanup precedence — suppressed aggregate/key errors.** The two T040
  cleanup blocks used `runCatching` and rethrew the original failure. They now
  call `cleanupIncompleteAggregate`, which treats `deleteTree == false` and
  `deleteAggregateKey == false` as failures, attempts both removals, and
  returns the first cleanup failure. Cleanup failure wins over the original
  failure (including `CancellationException`); the original is preserved only
  when cleanup succeeds; `Error` is never masked. The RED tests failed on
  `78f5432` with
  `unexpected exception type thrown; expected:<StorageWriteException> but was:<CancellationException>`
  for both the aggregate-delete and key-delete cases; both now pass and assert
  the `SAVE-003` residue state (aggregate directory or orphan alias retained,
  no visible document).

- **Interleavings.** The new tests cover cancellation during commit (above),
  a pre-first-chunk write failure (above), abort between write chunks, abort
  after the last chunk but before promotion, abort at the last checkpoint
  before meta, and the service-level cleanup-failure path. The last three
  behaviour tests were GREEN on `78f5432` because the existing abort checks
  already fired at those points; they are retained as coverage for the
  previously untested checkpoints. The service-level cleanup test is GREEN only
  after both the deadlock and cleanup-precedence fixes, so it is not presented
  as an independent RED.
- **Lock-order proof.** The service worker holds `lifecycle.lock` and only
  reads `OperationContext.isCancellationClaimed`, which reads the handle's
  `claimDecided` `AtomicBoolean` and never acquires the handle lock. All
  lock-taking handle access (`cancellationCleanupFailure`,

### Observed behaviour

- **Streaming shape:** a 2,097,152 + 12,345-byte source records multiple
  `HASH` chunks, each ≤ 65,536 bytes, and multiple `WRITE` chunks, each

  `tmp/` entry remains, and no store file contains the source's `%PDF-`
  plaintext marker.

  crossing the first 1 MiB boundary byte-identically, and a three-byte tail
  followed by `-1`.

  trailing byte fails with `InvalidDataException` (`SAVE-007` storage
  vocabulary) and leaves no aggregate when cleanup succeeds. A wrong expected
  hash at commit fails with `CorruptDataException` (`SAVE-003`) and leaves no

  `StorageWriteException` (`SAVE-003`), not the original cancellation; the test
  asserts the aggregate directory or orphan alias remains as reported residue
  while `list` stays empty.

- `NONE` is not a runtime evidence class. No Android runtime, emulator, device,

  needs the final plaintext length and chunk count before the first chunk can
  be authenticated. The source is opened read-only both times via the
  `PickedDocument` factory; a provider stream that cannot be reopened fails
  closed as `IMP-002`. No plaintext or intermediate ciphertext temp file is
  created.
- The `store.stageSource` channel bridge (ByteArray input) remains the
  materialized API for the synchronous `store.stageSource` channel method. T040's
  streaming path is `EncryptedStore.stageSourceFromStream`, used by
  `ImportService`; the channel method is not a streaming claim.
- Preflight uses PDFBox `MemoryUsageSetting.setupMainMemoryOnly()` and may hold
  the staged plaintext in memory while parsing; that is a preflight property,
  not a staging claim. The encrypted staging path itself is chunk-bounded.
- T039 reports null geometry for a page whose structure could not be read. The
  persisted `Page` model and the channel page shape still require a positive
  box, so such an unreadable page is persisted with a deterministic 1x1
  placeholder geometry, `unreadable = true`, and its `IMP-006` failure. The
  placeholder is never claimed as the original page geometry; T042/T044 must
  treat an unreadable page as non-renderable content and must not present the
  1x1 box as a real page size.
- A cancellation that wins after the final `meta.fx1` promotion cannot remove
  the now-visible document and may still yield the facade's `PLT-004` terminal
  result. The document is complete and verified, not partial; no user data is
  deleted. This residual race is narrower than the T038 interrupted-first-cancel
  window and is not claimed as fully eliminated.

  `SAVE-003` and deliberately leaves the incomplete aggregate or orphan alias
  for the startup sweep; it never reports a clean `PLT-004` with residue. The
