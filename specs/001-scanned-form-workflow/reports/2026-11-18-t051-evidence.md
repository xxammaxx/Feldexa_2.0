## 1. Scope

This report covers exactly T051 / issue #51: the 200 DPI grayscale page
raster analysis primitives in
`packages/feldexa_recognition/lib/src/raster.dart`, their host-VM tests in
`packages/feldexa_recognition/test/raster_test.dart`, and the single existing
T051 row in `reports/README.md`. It implements
`contracts/coordinates-and-geometry.md` §4 and the measurement primitives that
`contracts/recognition-output.md` §2.1 requires T052/T053 to consume.

**Review A correction round:** Review A found one blocking numerical defect
and boundary gaps in the original T051 slice. The correction replaces the
signed 64-bit `inkPixels * 100 > totalPixels * percent` comparison with an
exact [BigInt] comparison, defines and documents explicit raster extent caps
for `RasterSize`, `pointToPixel`, `PixelRect`, and `GrayRaster`, and adds nine
boundary/overflow tests. The original 52 tests and their semantics are kept
unchanged. This is still pure-Dart host-VM evidence; no detector, OCR,
platform rasterizer, Android runtime, or performance claim is added.

**Branch taken:** pure raster and measurement primitives, not detectors. The
task explicitly excludes OCR and ruling-line/box/table-grid/whitespace/
alignment detection. The library therefore maps page display sizes and points
to raster space, owns an immutable grayscale buffer, and exposes summed-area
luminance and ink-mask queries. It decides no field candidates and detects no
document structure.

What this run proves:

- The analysis raster is 200 DPI grayscale with `rasterScale = 200 / 72`,
  `widthPx = round(displayWidthPt × rasterScale)`, and
  `heightPx = round(displayHeightPt × rasterScale)`; A4
  (595.28 × 841.89 pt) rounds to 1654 × 2339 px.
- Pixel centres are at `i + 0.5`; `pixelCenterToPoint(i) =
  (i + 0.5) / rasterScale`; `pointToPixel` uses the documented
  `floor(point × rasterScale)` rule for accepted coordinates; every sampled
  centre in an A4-sized page round-trips to the same pixel with at most 0.01 pt
  of error.
- `GrayRaster` is immutable and no-alias: the constructor copies the supplied
  bytes, `pixels` is an unmodifiable view, stride is exactly the width with no
  row padding, and all pixel access is bounds-checked.
- The RGBA/BGRA factories are explicit about channel order, require opaque
  alpha, and use
  `luminance = (299 × R + 587 × G + 114 × B + 500) ~/ 1000`.
- `IntegralImage` builds exact summed-area tables; rectangle sums are O(1) and
  equal naive sums for every rectangle of a deterministic 17 × 13 pattern.
- `RasterAnalysis` measures exact ink counts below the documented default
  threshold 128 (`luminance < 128`), yields the exact fraction, and provides
  `exceedsPercent` with [BigInt] arithmetic. The huge-count tests prove that
  the 10 % / 25 % comparison returns false at `total = 2^60`, where both
  sides of the former signed 64-bit multiplication overflowed.
- `maxRasterExtentPx = 40000` and `maxRasterPixels = 1600000000` are
  documented and enforced. Raster dimensions, point coordinates, and
  `PixelRect` fields above the cap fail closed with a content-free
  `ArgumentError`; `1e20`, `1e100`, `1e308`, infinity, and NaN dimensions/
  points are rejected instead of saturating or throwing an implementation-
  defined conversion error.
- The complete host-VM package suite passes: 61 tests, 1 test file, 0
  failures, 0 errors, 0 skipped (52 before the Review A correction).

- No platform rasterizer, PDFium pixel buffer, Android runtime, emulator,

### Formulas, caps, and thresholds

| Item | Implemented rule |
| --- | --- |
| Analysis scale | `rasterScale = 200 / 72` |
| Raster dimensions | `round(displayWidthPt × rasterScale)` and `round(displayHeightPt × rasterScale)`; positive finite input; rounded dimension 1 … 40,000 px |
| Pixel centre | `(index + 0.5) / rasterScale` |
| Pixel edge | `edge / rasterScale` (half-open rectangle boundary) |
| Display point → pixel | `floor(point × rasterScale)`; nearest centre, boundary assigned to the right/lower pixel; accepted only when `point × rasterScale` is finite and `< 40,000`, so indices are `0 … 39,999` |
| Grayscale buffer | one byte per pixel, 0 = black, 255 = white, row-major, stride = width, no padding, no alpha; width and height 1 … 40,000 and total ≤ 1,600,000,000 |
| RGBA bytes | `R, G, B, A` per pixel, straight 8-bit channels, alpha must be 255 |
| BGRA bytes | `B, G, R, A` per pixel, straight 8-bit channels, alpha must be 255 |
| Luminance | `(299 × R + 587 × G + 114 × B + 500) ~/ 1000` (Rec. 601 integer approximation, half-up) |
| Ink | `luminance < threshold`; default threshold 128 means 0–127 ink, 128–255 background |
| Rectangle | half-open `[left, right) × [top, bottom)`; fields 0 … 40,000 for `left`/`top` and 1 … 40,000 for width/height; derived `right`/`bottom` ≤ 80,000 and `area` ≤ 1,600,000,000; out-of-raster access raises `RangeError`, never silently clamped |
| Integral image | `(width + 1) × (height + 1)` summed-area table; O(1) rectangle sums; `Uint32List` capacity documented and oversized rasters rejected |
| Ink coverage | exact integer `inkPixels` and `totalPixels`; `fraction = inkPixels / totalPixels`; `exceedsPercent` compares `inkPixels × 100 > totalPixels × percent` with `BigInt` on both sides |

Both sides are exact for any 64-bit integer count. Huge tests cover

### Determinism

The library imports only `dart:typed_data`. It uses no clock, randomness, file
or network I/O, locale, platform channel, or Flutter/`dart:ui` API. The
integral-image loops visit pixels in a fixed row-major order, BigInt
comparisons are exact and deterministic, and the only floating-point outputs
are the documented mapping functions and `InkCoverage.fraction`; all counts
and threshold comparisons are integer arithmetic.
