## 1. Scope

This report covers exactly T038 / issue #38: the SAF
`ACTION_OPEN_DOCUMENT` streaming import in
`apps/feldexa_app/android/app/src/main/kotlin/de/feldexa/app/import/ImportService.kt`
and its host Activity/provider seam in `MainActivity.kt`. It does not wire the
import into the channel and does not create a visible document or revision.

FR-001 is satisfied: `MainActivity` registers one
`ActivityResultLauncher<Array<String>>` over
`ActivityResultContracts.OpenDocument()` for MIME `application/pdf`, which
issues the ordinary `ACTION_OPEN_DOCUMENT` picker. Because `FlutterActivity`
extends the plain `android.app.Activity` (not `ComponentActivity`), the
launcher is hosted by a small concrete `ActivityResultRegistry` whose
`onLaunch` delegates to `startActivityForResult` and whose result is dispatched
from `onActivityResult`. No storage permission, custom browser, file path or
`File` conversion is used. The picked URI is consumed only through
`ContentResolver.openInputStream`, exposed by the narrow `PickedDocument`
seam. The `OpenableColumns.DISPLAY_NAME` query is resolved lazily, on the facade
worker thread that reads `displayName`, never on the main thread inside the
ActivityResult callback; the terminal value stays the same (name or null) and no
permission is added.

FR-095 is satisfied at the scope of this task: bytes read from the stream are
staged through the existing `EncryptedStore.stageSource` seam into app-private
encrypted storage. FR-009 is satisfied because a stage leaves the aggregate
incomplete (no `meta.fx1`/`head.fx1`), so a rejected or cancelled import is
never a visible document, draft, template or stored record.

`platform-channel.md` §2.4: the facade sends the start reply `{operationId}` and
publishes exactly one terminal result; `ImportService` returns only
method-specific data and never publishes a result. §3 terminal data produced by
T038: `sourceId`, `documentId`, `sha256`, `sizeBytes`, `displayName`.
`pageCount`/`pages` are deliberately absent — they are T039 PDF-preflight
outputs and inventing them would be out of scope. §3.2: the stream is counted
and SHA-256 hashed in bounded 64 KiB chunks with an 80 MiB (83,886,080-byte)
cap; exceeding it raises the existing `IMP-007` / `tooLarge` /
`import.tooLarge` mapping (no T045 wording, ARB key or catalog change).

`Context.checkCancelled()` is honored inside the read loop, after the loop,
during the picker wait, and in the post-staging cancellation decision. A
cancellation before staging creates no stage. A cancellation after staging runs
the registered staged-aggregate discard exactly once inside the operation
handle's cancellation linearization; a late registration (cancellation already
pending) runs the discard inside the same lock and records any failure before
terminal cancellation is observable. Cleanup is claimed and executed on the
facade's dedicated background paths, never on the channel/UI thread, and the
terminal publication reads the recorded failure inside its own critical
section. A failed discard is reported as the mapped non-cancelled storage
failure, not as a clean `PLT-004`. A repeated `cancel.operation` for an already
claimed operation is acknowledged immediately from a lock-free claim signal
(`{cancelled: true}`) without waiting on the cleanup-held handle lock; that
reply is a claim acknowledgment, not the terminal result, and the terminal
result still waits for cleanup and is published exactly once.
`import.verifySource` and `import.discardStaged` fail closed with
`PLT-001`/`platform.unsupported` — no wire shape is invented. Storage exceptions
are mapped with the same content-free codes/categories as `StoreService`.

Content rules follow `contracts/platform-channel.md` §2.2: no method result or
failure carries a URI, path, file name, document title, or source byte content.
The only content-bearing value produced here is the contract-specified
`displayName` in the success payload. No real document content, title or URI is
present in this report or in any test artifact; the only document-like strings
are the synthetic fixture labels named in the metadata input row.

Deferred: T039 (PDF parsing, preflight, page geometry, encryption detection,
`pageCount`/`pages`), T040 (true streaming encrypted copy and import commit /
`EncryptedStore.kt`), T041 (Dart error mapper — no Dart touched), T045 (IMP-007
wording/ARB/catalog changes), and all channel wiring.

#### Exact ordering and thread ownership

1. **Channel/UI thread** (`PlatformChannelFacade.handle`, `cancel.operation`):
   submits `claimTask` to `cancelClaimExecutor`, waits for the claim latch, then
   posts the `{cancelled}` reply. It never runs cleanup and never acquires the
   handle lock for storage I/O.
2. **Claim executor** (`OperationHandle.claimCancellation`): under the handle
   lock, an `ACTIVE` operation moves to `CANCELLING`; a registered cleanup is
   detached for the cancellation executor; a still-queued operation runs its
   cheap queued-cancel action inline (single terminal publication). The claim
   latch is signalled before cleanup is scheduled, so the channel reply never
   waits on cleanup.
3. **Cancellation executor** (`OperationHandle.runClaimedCleanup`): acquires the
   same lock, runs the detached discard, records a first-wins failure, moves to
   `CANCELLED`, and signals publication waiters.
4. **Service worker** (late registration, `setCancelCleanup`): if cancellation
   is already pending when `ImportService` registers after staging, the discard
   runs inside the lock here, records its failure and only then makes
   `CANCELLED` observable. If no cleanup is registered, the service's terminal
   publication folds `CANCELLING` into `CANCELLED`.
5. **Terminal publication** (`publishCancellation`): the single idempotent
   publisher reads `cancelActionFailure` *inside* its critical section. It waits
   for a claimed cleanup and publishes exactly one result, substituting the
   recorded `SAVE-*` failure for `PLT-004`.

#### Repeated-cancel and reply semantics

- **First cancel:** the handler sees no claim signal, submits the claim task,
  and waits for the claim handshake. Cleanup is detached (or late-registered by
  the service) and runs off the channel thread. The reply acknowledges that the
  cancellation claim is linearized; it may precede cleanup and is not the
  terminal result. The terminal result still waits for cleanup and is published
  exactly once.
- **Repeated cancel (same operation, after the claim):** the lock-free signal
  is already true. The handler replies `{ "cancelled": true }` immediately and
  never submits a claim task, so it cannot block on the cleanup-held handle
  lock. If a claim task was already queued before the signal became visible, it
  re-checks the signal and returns a true claim without acquiring the lock.
- **Completed operation:** the claim signal is false; `claimCancellation`
  observes `COMPLETED` and the reply is `{ "cancelled": false }` — no stale
  `true`.
- **Unknown/finished operation:** `operations.find` returns null and the reply
  is `{ "cancelled": false }`.
- **Terminal invariant:** `isCancelled` remains false during `CANCELLING`;
  terminal publication reads the cleanup failure inside its lock, waits for any
  claimed cleanup, and emits exactly one result. Repeated cancel replies do not
  publish a terminal result.

## 7. Limitations

- `NONE` is not a runtime evidence class. No Android runtime, emulator, device,
  SAF picker, staged decrypting reader, Keystore, MethodChannel, viewer, OCR,
  field detection, export or user journey was executed. This report does not
  claim any of them.
- `EncryptedStore.stageSource` accepts a materialized `ByteArray`, so T038
  reads the stream in bounded chunks but necessarily materializes the source
  in memory (bounded to ≤ 80 MiB) before staging. A true streaming encrypted
  copy is T040 and is not implemented here.
- T038 stages an incomplete source aggregate; it does not perform PDF
  preflight, commit `meta.fx1`/`head.fx1`, or create a visible document. Those
  are T039/T040. Consequently `pageCount`/`pages` are absent from the terminal
  data.
- `import.verifySource` and `import.discardStaged` intentionally report
  unsupported until T039/T040 define their wire shapes.
- Cancellation is a `CANCELLING` claim until cleanup finishes. `isCancelled`
  and the terminal result stay false/unpublished; services must use
  `checkCancelled`/progress to abort. Only `ImportService` reads
  `isCancelled`, and it does so after registering its cleanup. Round 3 replaced
  the round-2 repeated-cancel lock wait with the lock-free claim fast path; the
  round-2 first-cancel handshake and executor-saturation notes still apply.
- The cleanup holds the handle lock for its duration. `isCancelled` and
  terminal publication wait for it, and progress aborts independently through
  `isCancellationRequested`. A repeated `cancel.operation` does not acquire the
  lock once the lock-free claim signal is visible. The cleanup is bounded to
  one incomplete aggregate's local objects and performs no provider query or
  network I/O.
- The `cancel.operation` reply is emitted after the claim is linearized but
  before a claimed cleanup finishes. It reports that cancellation won, not the
  terminal result; the terminal result waits for cleanup and is published
  exactly once. A repeated cancel replies `true` immediately and publishes
  nothing.
- The first cancel still waits for the claim handshake on the single claim
  executor and may wait on the handle lock if a terminal publication holds it;
  this is not storage cleanup, but it is a real bounded wait. A repeated cancel
  submitted before the claim signal is visible may wait for that already-queued
  claim task, which short-circuits without acquiring the handle lock. If both
  dedicated executors are saturated or a prior cleanup is queued ahead, the
  first reply and the terminal result can be delayed; the claim/cleanup are
  never queued behind the target operation's keyed serial queue. Executor
  rejection falls back to the claim thread (off-channel) or, in the extreme
  claim rejection case, the channel thread.
- The two dedicated executors (the claim executor and the cancellation
  executor) are daemon-backed and are shut down by `dispose()`; a cleanup
  accepted before shutdown still runs before the pool drains.
- If the discard fails, the terminal result is the mapped non-cancelled storage
  failure (`SAVE-*`), while the `cancel.operation` reply still reports
  `cancelled: true` because the cancellation itself won. The aggregate is then
  retained and remains invisible (no meta); the existing startup sweep is the
  fallback. The failure is recorded, never swallowed.
- The SAF picker itself was not instrumented: no emulator/device run, so the
  Activity-result path is verified only by construction and by the
  injectable-seam unit tests. The picker callback is exercised through a fake

- The Android source compiles through the Gradle unit-test task, but no APK was

  device, instrumentation, performance or user-journey claim.
- The `gradlew.bat` line-ending modification is pre-existing working-tree state
