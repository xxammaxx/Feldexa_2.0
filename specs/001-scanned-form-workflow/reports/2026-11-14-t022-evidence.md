## 5. Results

`ExportPlan` implements `contracts/export-plan.md` §2 as a canonical JSON model:
`schemaVersion`, `documentId`, `revisionId`, `sourceSha256`, `pageCount`,
`evidenceClass`, `font`, `pages`, `warnings`, and `info`. It enforces schema
version 1, lowercase UUIDv4 ids, 64 lowercase hex source SHA-256, 1–100 pages,
contiguous page indexes, one op per field, relative bundled font paths, and the
string evidence token `simulated | emulator | device | none` (so the package
never imports `feldexa_ports`).

Each page derives `displaySize` and the display→PDF `ctm` from the T016
`PageGeometry`; a serialized CTM is accepted only when it matches the normative
matrix, and each op's `pdfRect` is accepted only when it equals the geometry
mapping of the display `rect`. The sealed `ExportOp` hierarchy keeps the T018
`Provenance` vocabulary and implements §2.2: the 7–12 pt text clamp, positive
line height, baseline inside the field rectangle, `#000000` only, non-empty
materialized lines, no trailing spaces, no embedded newline, `overflow == false`
(`EXP-001` blocks before a plan exists), the checkbox inset/stroke clamps, and
the fixed image `contain`/`center` contract.

Forbidden §2.3 content is refused recursively: values, signatures, suggestions,
OCR text, screenshots, labels, AcroForm/form fields, widgets, and annotations.
Other unknown same-schema JSON fields are preserved at every modeled level
(`data-model.md` §6), including the CTM.

`ExportValidation` is the blocking result of `PdfExportPort.validate`: it
carries `warnings` and UTC `validatedAt`, derives `isValid`/`isBlocking`, and
each warning carries one of the seven blocking codes (`EXP-001`–`EXP-006`,
`SAVE-001`), a machine `reason`, and optional `fieldId`, `pageIndex`, and
`fieldLabel`. `fieldLabel` is user content, is excluded from `toString`, and is
never logged.

`ArtifactVerification` carries the five §3.15 checks and UTC `checkedAt`.
`ExportArtifact` starts only in `validating` and exposes exactly these
transitions:

```text
validating --startRendering--> rendering
rendering  --startVerification--> verifying
validating/rendering/verifying --fail--> failed
verifying  --succeed (all checks pass)--> succeeded
succeeded  --markDeleted--> deleted
```

`failed` and `deleted` are terminal. There is no shortcut from `validating` or
`rendering` to `succeeded`. `succeed` requires all five checks, a positive byte
size, a valid SHA-256, a page count, and a verification that does not predate
the attempt; `failed` requires a catalog failure code and clears byte size and
hash. `fromJson` re-applies the same invariants, so a hand-written `succeeded`
record without an all-passing verification is refused. `isPreviewAvailable` is
true only for `succeeded`; `markDeleted` is the only path from `succeeded` and
removes preview availability while retaining verified metadata.

The `data-model.md` §3.15 diagram's `blocked` outcome produces no artifact. When
an attempt record exists, T022 represents it as terminal `failed` with one of
`EXP-001`, `EXP-003`, `EXP-004`, `EXP-005`, or `EXP-006`; `isBlocked` exposes
that distinction. `EXP-002` and `SAVE-001` remain failures, not preflight
blocks. This avoids adding a persisted state outside the §3.15 field table.

`contracts/export-plan.md` §2's example uses `baselineFromTopPt: 8.1` for
`fontSizePt: 8.7`, while §2.2's formula `1.5 + 0.8 × fontSizePt` evaluates to
`8.46`. T022 accepts the example by validating only the documented upper bound
(`baselineFromTopPt ≤ rect.height`) and leaves the exact layout formula to the
T103 builder. This is a documentation inconsistency, not a claimed acceptance
result.

- This is host-VM and static-analysis evidence only (`NONE`). It cannot prove
  PDFBox flattening, Android export, preview lifecycle, save/share/print,
  storage-pressure behavior, or device acceptance.
- The model is the T022 contract. It does not implement the T102 schema contract
  test file `packages/feldexa_export/test/export_plan_test.dart`, the T103
  layout builder, the T104 PDFBox applier, the T105 external verifier, or the
  T106/T108 preview and failure flows. Those tasks consume these types later.
- `ExportPlan.warnings` is a string list because `contracts/export-plan.md` §2
  only shows an empty `warnings` array and defines no warning object. Field
  labels and machine reasons are modeled in `ExportValidationWarning`, where §4
  defines them; the plan model deliberately refuses label keys.
- The state diagram's `blocked` has no artifact; T022 records it as terminal
  `failed` with a blocking code when an attempt record exists, as described in
  §5. No additional persisted state is invented.
- The pre-existing host-SDK read-only condition was handled with the
  git-ignored shim; no toolchain installation or network access changed the
  candidate.
