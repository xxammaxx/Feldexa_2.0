## 3. Contract points NOT covered by this task

`contracts/export-plan.md` §5:

- **§5 step 2a flattening has no positive test here.** The code flattens an
  existing AcroForm in memory (`PDAcroForm.flatten`) and blocks with `EXP-002`
  when the appearances cannot be flattened (no single page can be named, so
  `EXP-006` was not used). Only the instrumented export run can prove the
  flattening on a real form PDF.
- **§5 step 8 source integrity is checked twice, and both checks live in the
  applier.** The stored source is hashed before the first write and again after
  the atomic rename, and both hashes must equal `plan.sourceSha256`; a mismatch
  is `EXP-005`, nothing is published, and the `finally` removes the renamed
  file. The second check re-reads the stored source through the content port —
  it is not a re-hash of the in-memory array. Neither check has host-JVM
  coverage, because `PdfExportService` needs PDFBox and the Android runtime;
  only the instrumented export run (T108/T109) executes them. **§5 step 8
  external checks are not part of the applier**: `qpdf --check`, Poppler/MuPDF
  side-by-side rendering, the 150 dpi masked comparison, the ≤1 mm placement
  tolerance, and the 300 dpi printability run belong to T105/T112/T110 and are
  **not** claimed here.
- **Byte-level determinism is not attempted** (as §5 states, only geometry,
  text, checkbox states, and signatures must be exact).
- **Memory-bounded source loading**: the source is loaded through
  `EncryptedStore` into a `ByteArray` (bounded by the 80 MiB import cap). The
  applier does not stream pages; PDFBox holds the document in memory.
- **Cancellation granularity** is per page and per phase (plus before the
  rename), not per op.

## 4. Open gap: FLAG_SECURE (contract §11 point 7) — deliberately not implemented

`contracts/platform-channel.md` §11 point 7 requires `MainActivity` to set
`FLAG_SECURE` on the editor/export routes. It is **not implemented** in this
task, on explicit parent decision (2026-11-25), because there is no Dart→native
route signal to hang it on:

- the app uses no named routes: every navigation is a `MaterialPageRoute`
  without `settings.name` (`editor_screen.dart`, `field_value_sheet.dart`,
  `start_screen.dart`), so `flutter/navigation`'s `routeInformationUpdated`
  carries nothing usable;
- the method catalog has no security/route method, and `METHOD_PREFIXES` is the
  closed set `{import, store, ocr, export, delivery}` (§11 point 5: "the channel
  surface is closed");
- `apps/feldexa_app/lib/features/export/` is empty (the preview belongs to T106).

A native-only approximation (secure while a session artifact exists) would cover
the export/preview routes but not the editor, and would over-claim coverage.
No checklist entry was marked done, no contract file was changed, and no dead
method spec was added. The UI slice that adds the export preview will introduce
the caller and the channel method together; then `FLAG_SECURE` is a single
additional call in `MainActivity` (`window.addFlags(WindowManager.LayoutParams.FLAG_SECURE)`
when entering a sensitive route, cleared on leave) — `PdfExportService` needs no
change for it.

## 5. Deviations worth knowing (not gaps)

- **`export.validate` response**: §4 lists only *blocking* codes, so a failing
  plan is reported as its catalog code (`EXP-001/003/004`) and a clean plan
  returns `{ ok: true, warnings: [] }`; the `warnings` array is never populated
  because a non-empty set would be blocking anyway.
- **`delivery` user cancellation** returns `{completed:false, cancelled:true}`,
  not an exception. `DEL-001` exists in the catalog ("no message") and the
  existing Dart `AndroidDeliveryClient` explicitly treats cancellation as
  `completed:false`, not as an error; throwing `DEL-001` would surface an error
  for a normal user action. `delivery.failed` (`PLT-001`/`internalError`) and
  `delivery.unavailable` (`PLT-001`/`deliveryUnavailable`) are used for real
  failures and missing targets.
- **Provenance record** is written as XMP (`feldexa:fieldProvenance`,
  `https://feldexa.de/ns/export/1.0/`) containing only
  `{page, ordinal, provenance}` tuples. An Info-dictionary key with the
  contract's `Feldexa/FieldProvenance` spelling is not usable because a PDF name
  cannot carry a `/`.
- **Unknown artifact ids** in `readArtifact`/`deleteArtifact` → `EXP-002`
  (plans); in `delivery.save/share/print` also `EXP-002` (delivery has no code
  of its own for a missing artifact).
- **`EXP-003/004/005/006/DEL-001` are not mapped** in
  `packages/feldexa_adapters_android/lib/src/android_channel.dart`
  (`throwAndroidChannelError` rethrows them unchanged). That is the Dart
  adapter's task, not this one.
- **`delivery.print` answers at hand-off, not at print time.** The response is
  `{completed:true, cancelled:false}` as soon as the system print UI has been
  opened; the print system is the authority on whether the document is printed,
  and the channel answer says nothing about that. A user who cancels inside the
  system dialog therefore still sees `completed:true` from `delivery.print`.
  No `DEL-*` code is invented for it: the catalog has no "print cancelled" entry
  and the Dart `AndroidDeliveryClient` maps the reply's `completed` flag straight
  into `DeliveryOutcome.completed`, with no print-specific terminal state.
- **`assertPlannedTextExtracted` checks the document, not a page.** The §5 step 8
  text check extracts the whole artifact (one `PDFTextStripper` run) and asserts
  that every planned line occurs somewhere in that text. A planned line that was
  drawn on the wrong page therefore passes this check; the per-page geometry and
  glyph checks are what localise it, and the masked side-by-side rendering
  (T105/T112) is the check that would catch a misplaced line.
- **The print adapter writes the whole artifact and ignores page ranges.**
  `PdfArtifactPrintAdapter.onWrite` copies every byte of the verified file and
  always reports `PageRange.ALL_PAGES`; the `pages` argument — the ranges the
  user selected in the system dialog — is not evaluated. Selecting "pages 1–3"
  therefore spools the full document. Honouring ranges would mean re-building a
  subset PDF, which `contracts/export-plan.md` §5 step 2 rules out (every source
  page is imported unmodified and never re-rendered or rebuilt); if the app is
  expected to honour ranges, that is a contract change, not an adapter fix.
- **`PdfArtifactPrintAdapter` has no automated coverage today.** T110
  (`integration_test/print_test.dart`) is the test that will cover the adapter
  through `PrintManager` and it is still open; `DeliveryServicePrintTest` covers
  only the `DeliveryService`→`DeliveryHost` wiring, and `src/androidTest`
  contains no `PrintManager`/`PrintDocumentAdapter` test.
