## 6. Contract analysis

The test deliberately does not import the T007 generator. It reads the bundled
TTFs and `metrics.json` directly and re-derives the contract with a second Dart
implementation of the sfnt tables the schema uses:

- `head` (`unitsPerEm`), `hhea` (ascender/descender/line gap, `advanceWidthMax`,
  `numberOfHMetrics`), `maxp` (`numGlyphs`), `hmtx` (per-glyph advances),
  `cmap` format 12 (Unicode coverage), and `OS/2` (weight class, typographic and
  Windows metrics, x-height, cap height).
- The comparison is exact, not tolerant: all **3,094** mapped codepoints per
  weight must have the same key set and the same integer advance in the JSON
  and the TTF-derived table.
- A present key means the glyph exists; its value is the `hmtx` advance in
  design units. A missing key is an `EXP-004` coverage failure, not a zero
  width. U+0301 is present with advance 0 as a real combining mark.
- Width in points is `sum(advance[cp] for cp in text.runes) * fontSizePt /
  unitsPerEm`; schema v1 intentionally has no kerning or ligatures, matching
  the plain advance sum PDFBox uses.
- The single-line clip rule is `measuredWidth > rect.width − 3.0` (1.5 pt
  padding on both sides), from `contracts/export-plan.md` §3.1.

The bundled table itself reports:

| Property | Regular 400 | Bold 700 |
| --- | --- | --- |
| Asset | `assets/fonts/NotoSans-Regular.ttf` | `assets/fonts/NotoSans-Bold.ttf` |
| Bytes / SHA-256 | 790,500 / `97eaf070…1221c9` | 802,504 / `53b53721…8e8039` |
| `unitsPerEm` | 1000 | 1000 |
| Glyphs / full `hmtx` records | 4,671 / 4,665 | 4,671 / 4,665 |
